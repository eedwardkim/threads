# Threads project notes

## Toolchain and verification

- Use Node 22 LTS and npm. The pinned runtime is in `.nvmrc`. If the system Node is newer, use `npm exec --yes --package=node@22.23.2 --package=npm@11.19.1 -- npm <command>`.
- Local development uses the same stack as production: Supabase Postgres + Supabase Auth. Start local Supabase, copy `.env.example` to `.env.local`, run `npm run db:migrate` once, then `npm run dev`. There is no SQLite fallback; missing `DATABASE_URL`/Supabase configuration fails loudly.
- Verification: `npm test` (unit + Postgres projects), `npm run test:pg`, `npm run test:e2e` (Playwright against a production build on :3100, or `E2E_BASE_URL` for a hosted preview), `npm run perf` (deterministic mock load harness), `npm run typecheck`, `npm run lint`, `npm run build`. Postgres/e2e/perf tests create fresh random owners and disposable Auth users; they never truncate or reset shared data and must only target local Supabase or a database explicitly designated for testing.
- Tailwind source discovery is explicitly limited to `app` and `components`. Keep generated files out of the CSS dependency graph.

## Database and identity

- Schema lives in `db/migrations/*.sql` (versioned, additive, tracked in `threads.schema_migrations`) and is mirrored in `lib/db/schema.ts` (Drizzle, `pgSchema("threads")`). Migrations run only via `npm run db:migrate` (`DIRECT_DATABASE_URL`, session pooler/direct) — never at import, cold start, `next build`, or inside requests. Existing `public` tables from older deployments are left untouched.
- Runtime connections (`lib/db/client.ts`) use `DATABASE_URL` (transaction pooler), a small bounded pool reused per warm instance, prepared statements off, TLS validated (`sslmode=disable` allowed only for loopback hosts). Never hold a transaction or checked-out connection while waiting on a model.
- Identity is centralized in `lib/db/session.ts` (`withUser`): each unit of work is one transaction that runs `SET LOCAL ROLE threads_app` plus transaction-local `request.jwt.claims`; `threads.current_user_id()` reads them. `threads_app` is nologin/nobypassrls, so RLS applies to every runtime query, and identity resets on commit or rollback (tested in `tests/pg/rls.test.ts`). Do not connect as `service_role`, and do not add `bypassrls` roles.
- `lib/db/repository.ts` additionally scopes every query by `owner_id`; composite owner-aware foreign keys make cross-owner references impossible at the constraint level. Completed message content is immutable (trigger). Main and thread queries stay strictly separated. Ordering timestamps are allocated as max+1 under a per-owner transaction advisory lock (`nextCreatedAt`), never an unprotected `SELECT MAX`; historical demo/import timestamps use the explicit `preserveTimestamp` option.
- Auth is Supabase SSR (`lib/auth/server.ts`, `proxy.ts`, `app/login`, `app/auth/*`). Identity is always verified server-side; APIs return JSON 401/403 via `lib/api.ts` (`withApiUser`, `apiError`), never HTML redirects. Private responses carry `Cache-Control: private, no-store`. Same-origin checks in `lib/api.ts` use the request host (no origin allowlists); `lib/auth/redirect.ts` sanitizes `next` targets.

## Generation, streaming, and limits

- Concurrency control is durable Postgres state in `lib/db/jobs.ts` (`threads.generation_jobs`): owner + scope admission, request-id idempotency with payload-hash mismatch rejection, lease renewal (also during prefill), `cancel_requested` for cross-instance Stop (`DELETE /api/generate?id=`), a fence from `threads.generation_fence_seq` that stale checkpoints/finalizers/usage writes must match, and per-user/per-minute/total limits in the same tables. There is no process-global lock; do not reintroduce one.
- `lib/generation.ts` streams NDJSON, forwards text immediately, and persists through a single-in-flight coalescing checkpoint writer (400 ms interval / byte threshold). Finalization drains the writer, normalizes math only on success (`lib/math.ts`), commits the final immutable source, and emits `finish` only after the commit. Stop/failure keeps the last safely persisted partial as incomplete; the whole run stops at `deadlineMs` (280 s) before `maxDuration` (300 s). `GET /api/generate?id=` reconciles an accepted request whose response was lost.
- `lib/stream-store.ts` keys browser streams by user + chat + scope and survives panel unmounts; `lib/chat-cache.ts` and `lib/client-state.ts` are user-scoped and are cleared on sign-out/account change (stale responses are discarded by identity/revision).
- `components/markdown.tsx` caches parsed trees for completed (immutable) content in a bounded module LRU; `.message` uses `content-visibility: auto`. Keep both when touching message rendering — cached navigation targets depend on them.
- `lib/markdown-offsets.ts` owns all source-position mapping and anchor rendering. Accept only verified raw offsets; transformed text that cannot be mapped exactly fails closed. Never normalize at render time or rewrite existing completed messages — thread anchors use persisted offsets.
- API model IDs belong only in `lib/models.ts`; persist stable model keys. Provider credentials and mode are server-only; `USE_MOCK=true` is explicit and refused in Vercel production unless `THREADS_ALLOW_MOCK_IN_PRODUCTION=true`. The compression provider is `THREADS_COMPRESSION_PROVIDER` or the first configured of DeepSeek → Anthropic → OpenAI. The DeepSeek adapter keeps the system-message guard and the isolated thinking mapping in `lib/provider.ts`. Verify Anthropic model availability with its Models API; Opus omits sampling overrides and keeps an explicit 32,000-token response limit.
- Frozen context metadata is stripped before prompt assembly. Usage attribution must not change briefing text or prompt bytes; explicit context refresh invalidates old usage attribution. Thread creation, copy-to-main, folder moves (cycle checks), auto-title vs. rename, and demo hydration are single short transactions.

## Demos and import

- `lib/demo-catalog.ts` holds only lightweight metadata. Demo folders/chats are per-user instances identified by `demo_key` (unique per owner); `lib/seed.ts` hydrates one requested demo chat atomically from a dynamically imported fixture with bulk inserts, safe under concurrent requests. Never import the full corpus into client components or hydrate every conversation on login. Library → Restore demos adds only missing items and never overwrites names, moves, follow-ups, resolutions, or deleted-thread state. Demo replies use null model keys and are labeled Prewritten.
- `lib/import/sqlite.ts` / `npm run db:import-sqlite` is the only SQLite code path: read-only WAL-consistent source, explicit `--user`, `--dry-run`, id preservation with reported remaps, hash/anchor/foreign-key validation, idempotent reruns. `better-sqlite3` is a dev-time tool dependency; the Vercel runtime never touches SQLite.
- Conversation/folder naming uses `components/name-dialog.tsx`: save explicitly and keep failed drafts open. The first main message auto-titles only a chat still named `New chat`; preserve custom names and folder placement.
- `tests/demo-content.test.tsx` renders every demo anchor and equation and executes the documented CS61A examples when Python 3 is available; keep stdout and expected exception classes synchronized with the displayed code.

## Deployment

- Vercel functions are pinned to `yul1` in `vercel.json` to sit next to the Supabase project in `ca-central-1`. Configure Preview and Production environment scopes separately (names in `.env.example`). Apply migrations to the target database before deploying dependent code; never from the build.
